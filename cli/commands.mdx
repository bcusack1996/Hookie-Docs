Most of this CLI is **generated**. Commands, flags, help text and validation all come from the tool catalog that also defines what a [connected agent](/connected-agents) can do — so the console, your agent and your terminal are one API, and a new capability appears in all three at once rather than in whichever one someone remembered.

Which is also why this page is worth trusting: it is produced from that catalog rather than written alongside it.

## Reading it

```bash
hookie <group> <verb> [flags]
hookie <group>                 # means <group> list
hookie <group> --help          # the group's commands
hookie <group> <verb> --help   # usage, the flags with their types and which are required, and an example
hookie help <group> <verb>     # the same
```

Every command has its own help, the hand-written ones included: `hookie replay --help` shows `--since`, `--failed`, `--destination` and `--limit` with an example, and `hookie login --help` shows `--scope`, `--no-open`, `--name` and `--reregister`.

- `*` marks a **required** flag.
- ⚠️ marks a command that **asks before acting**. That gate reads the tool catalog, never the word "delete". `hookie workflows delete` only deactivates, and an update undoes it, so it asks only with `--permanent`. `hookie keys revoke` destroys a credential and has no "delete" in its name.
- A flag name is the API field in kebab case, so `webhook_id` is `--webhook-id`. Where two sibling routes spell the same field differently — create takes `datasetFilter`, update takes `dataset_filter` — the **flag** is the same on both and the CLI sends whichever spelling that route wants.
- **An unknown flag is an error**, with a suggestion. `--datset orders` would otherwise be a successful call that quietly did the wrong thing.

Every command also takes the global flags: `--url`, `--project`, `--json`, `--reveal`, `--redact`, `--yes`, `--quiet`.

<Note>
  `--project` takes a **slug or an id**. Project-scoped commands use your workspace’s Default project when it is omitted. Workspace-wide commands do not acquire a project restriction. In CLI **0.3.1 and later**, for `memories save`, `memories list` and `memories update`, an explicit `--project` sets or filters the optional project link; omitting it leaves a new memory unlinked, lists without that filter, or preserves an existing link. There is deliberately no `--project-id`: two ways to say the same thing, one of which silently 404s on a slug, is worse than one.
</Note>

## Hand-written commands

These are not single API calls, so they are not generated. [Operations](/cli/operations) covers them in full.

| Command | |
| --- | --- |
| `hookie login` · `logout` · `whoami` · `status` | Connect this machine, and see what it is connected to. |
| `hookie send --endpoint <x> --data @f.json` | Send a test event to an endpoint's public URL. |
| `hookie replay <id>` · `replay --since 1h --failed` | Redeliver one, or a window. |
| `hookie open --project x --tab deliveries` | Open the console at a project. |
| `hookie apply -f hookie.yml` · `hookie diff -f hookie.yml` | Converge a project on a file, or show what that would change. See [Configuration](/cli/configuration). |
| `hookie export [--format yaml\|json] [-o file]` | Write a project's configuration as a file that `apply` and `diff` read. See [Configuration](/cli/configuration#start-from-what-a-project-already-has). |

## Two that are narrower than they look

`hookie workflows update` is a **full replace**, not a patch — which is why `--name`, `--entry-dataset` and `--steps` are all required. Omitting one would drop it. Read the current definition first:

```bash
hookie workflows get --workflow-id wf_123 --json > wf.json
# edit wf.json, then send the whole thing back
hookie workflows update --workflow-id wf_123 \
  --name "$(jq -r .name wf.json)" \
  --entry-dataset "$(jq -r .entry_dataset wf.json)" \
  --steps @wf-steps.json
```

`hookie endpoints update` changes an endpoint's name, dataset, enabled state, IP allowlist, form redirect, allowed origins and URL verification, but never its slug, criteria or mappings. The slug is part of the credential in its public URL, and the criteria and mappings define what it has already ingested — changing those in place would quietly reinterpret history. To change them, publish a new version with `hookie endpoints version`.

`hookie rules update`, by contrast, changes any field of a rule, conditions and mappings included, and sends only the flags you pass. Try a rule before you save it in the console's rule editor, or with `POST /admin/api/projects/{project_id}/rules/test`.

## JSON flags

A flag whose value is a list or an object takes JSON, or `@file.json` to read it from disk — which is how a workflow's steps get past your shell's quoting:

```bash
hookie rules create --name Orders --dataset orders \
  --conditions '[{"path":"type","equals":"order.created"}]' \
  --mappings @mappings.json

hookie rules update --rule-id r_123 \
  --conditions '[{"path":"total","op":"gte","value":100},{"path":"country","op":"in","value":["US","CA"]}]'

hookie workflows create --name Scoring --entry-dataset leads --steps @steps.json
```

A Slack or S3 destination's `--config` holds a credential, so read it from a file rather than typing it, where it would land in your shell history:

```bash
hookie destinations create --name "Orders channel" --type slack --config @slack.json --dataset-filter orders
hookie destinations create --name Archive --type s3 --config @s3.json
```

A list of plain strings also takes a comma-separated list, because `'["orders","shipments"]'` is a quoting puzzle with no upside:

```bash
hookie destinations create --name Warehouse --url https://wh.internal/h --dataset-filter orders,shipments
hookie destinations update --destination-id d_1 --dataset-filter null   # null means all datasets
```
