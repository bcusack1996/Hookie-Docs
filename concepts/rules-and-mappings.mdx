A **rule** decides which dataset a keyed event lands in and what shape it takes. Rules are for senders that can't say where an event belongs, such as one stream that carries orders, refunds and signups.

<Warning>
  Rules run on exactly one kind of request: an ingest key with **no dataset in the path**, `POST /v1/ingest/{key}`. They are never consulted for an endpoint URL, for `/v1/webhooks/{key}/{slug}`, or for `/v1/ingest/{key}/{dataset}`. Those requests already name their dataset. Adding a rule and then posting to an endpoint URL is the one setup that looks like it should work and doesn't.
</Warning>

## How rules route an event

When a keyed event arrives with no dataset:

1. Every **enabled** rule in the project is tried against the payload.
2. A rule matches when **all** of its conditions hold. A rule with no conditions matches every event.
3. Every matching rule writes its own record into its own dataset. Rules are not first-match, so one event can land in several datasets at once.
4. If no rule matches, no record is made. The response has `"routed": []`, and the raw submission is still stored, so you can find it under **Observability**.

```bash
curl -X POST 'https://app.hookie.ai/v1/ingest/ik_live_xxx' \
  -H "Content-Type: application/json" \
  -d '{"type":"refund","order":1042,"total":59.9}'
```

## Add a rule

On a project's **Rules** tab, choose **Add rule** and fill in:

| Field | What it does |
| --- | --- |
| **Name** | A label for the rule. |
| **Dataset** | Where matching events are stored. Pick one of the project's datasets or type a new name. |
| **Conditions** | What an event must contain, one row per condition. No conditions matches every event. |
| **Mappings** | Which fields to keep, as **Payload path** and **Record key** rows. No mappings stores the payload unchanged. |
| **Status** | Enabled or disabled. Only enabled rules run. |

Before you save, paste a **Sample event (JSON)** and choose **Test rule**. It shows **Matched** with the record the rule would store, or **Not matched**, and writes nothing. Choose **Create** to save.

Each rule's menu has **Edit**, **Duplicate**, **Enable** or **Disable**, and **Delete**. Rules have no order: every enabled rule that matches writes its own record.

The same rules can be managed with the [admin API](/api-reference#admin-api) (`PATCH …/rules/{id}` edits any field, and `POST …/rules/test` runs the same test) or a [connected agent](/connected-agents).

## Conditions

A condition tests one field of the payload:

```json
[
  { "path": "type", "equals": "refund" },
  { "path": "total", "op": "gte", "value": 100 },
  { "path": "customer.tier", "op": "in", "value": ["gold", "platinum"] }
]
```

- `path` is a field path, with dots for nested fields, read from the event as it was sent.
- `op` is one of `equals`, `not_equals`, `contains`, `exists`, `gt`, `gte`, `lt`, `lte`, `in` (a list of 1 to 100 values) or `regex`. `{ "path": "type", "equals": "refund" }` is shorthand for `op: "equals"`.
- In rules, `equals`, `not_equals` and `in` compare values **as text**, so `"42"` and `42` match. `gt`, `gte`, `lt` and `lte` compare numbers only.
- A `regex` is at most 200 characters, can't use backreferences or nested repetition, and tests only the first 256 characters of the field.
- Every condition in the list must hold. A rule takes up to 50.

Conditions use the same operators everywhere: in rules, endpoint criteria, [workflows](/workflows), and AI and WebSocket triggers. In workflows and triggers, `equals`, `not_equals` and `in` compare exact values rather than text.

## Mappings

A mapping copies one field of the payload into the record, under a key you choose:

```json
[
  { "path": "order", "key": "order_id" },
  { "path": "customer.email", "key": "email" }
]
```

With these mappings, the payload `{"type":"refund","order":1042,"customer":{"email":"ada@example.com"}}` becomes this record:

```json
{ "order_id": 1042, "email": "ada@example.com" }
```

Fields you don't map are left out of the record, but the full payload is still kept in the submission. With no mappings, the record is the whole payload. A rule takes up to 50 mappings, and each key can be used once.

## Endpoint criteria

An [endpoint](/concepts/endpoints) can have conditions and mappings of its own, called **criteria** and **mappings**. They work like a rule's, but they apply to that endpoint's events only, and the dataset is always the endpoint's own. An event that fails an endpoint's criteria is kept as a submission and makes no record.
