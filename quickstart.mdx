## 1. Create a project & endpoint

[Sign in](https://app.hookie.ai/#/signin) with an emailed 6-digit code or GitHub. There is no password; the first sign-in creates a free workspace. Then click **Create Project**, then open the project's **Endpoints** tab and **Add Endpoint**. Hookie generates a high-entropy webhook URL. The URL itself is the secret, so anyone who has it can send events:

```http
https://app.hookie.ai/{workspace}/{project}/{webhook}
```

The **Overview** tab shows the full URL with a copy button and a ready-to-paste curl example.

## 2. Send an event

POST any JSON to your endpoint URL. The whole payload is stored into the endpoint's dataset:

```bash
curl -X POST 'https://app.hookie.ai/your-workspace/orders/aBcXyz…' \
  -H "Content-Type: application/json" \
  -d '{"order":1042,"email":"ada@example.com","total":59.9}'
```

You'll get back the submission ID and where it routed:

```http
201 Created
{
  "submission_id": "9d3f…",
  "routed": ["orders"],
  "records": 1
}
```

## Or point an HTML form straight at it

An endpoint accepts what a browser actually posts, so a plain form needs no JavaScript and no backend of your own. Set `action` to your endpoint URL and you are done:

```html
<form action="https://app.hookie.ai/your-workspace/contact/aBcXyz…" method="post">
  <input name="name" required>
  <input name="email" type="email" required>
  <textarea name="message"></textarea>
  <button>Send</button>
</form>
```

The fields arrive as an ordinary record, stored whole into the endpoint's dataset:

```json
{
  "name": "Ada Lovelace",
  "email": "ada@example.com",
  "message": "Hello, world!"
}
```

Both form encodings work: `application/x-www-form-urlencoded` and `multipart/form-data`. A few details worth knowing:

- A field that repeats (checkboxes, a multi-select) becomes an **array** rather than losing all but one value.
- Field names are kept **verbatim and flat**. A field called `user.email` stays the key `user.email` and does not become a nested object, so a mapping rule sees exactly what the form sent.
- A **file** part is recorded as a descriptor and its bytes are discarded, in the record **and** in the raw submission kept under Observability. Hookie stores records, not blobs, so you get proof something was attached without the contents:
  ```json
  {
    "email": "grace@example.com",
    "attachment": { "filename": "report.pdf", "type": "application/pdf", "size": 18244 }
  }
  ```
- Everything else is still parsed as JSON regardless of its `Content-Type`, which is what most webhook providers send. A body that is not JSON but is sent as text, such as `text/plain`, XML, CSV or NDJSON, is stored as `{ "body": "<the text>", "content_type": "text/plain" }`. See the [API reference](/api-reference#ingest).

### Send visitors to a thank-you page

Because the browser navigates to the endpoint on submit, a visitor would land on Hookie's JSON response. Give the endpoint a **redirect URL** instead: open **Endpoints**, choose **Edit…** in its menu, and set **Redirect after a form submit** to your page (it must be `https://`). A native form post is then answered `303 See Other` to that page once the submission is stored. `fetch()` calls and server senders still get the JSON, and a resubmitted form that was already stored is sent to the same page.

### Submit with fetch()

To keep the visitor on your page, submit with `fetch()`. A browser only lets a page read the answer from an origin that allows it, so add your site under **Allowed browser origins** in the same form: one origin per line, such as `https://example.com`, or `*` for any page. Nothing is allowed by default. For an allowed origin the endpoint answers the `OPTIONS` preflight that a JSON body triggers, and every response carries `Access-Control-Allow-Origin`, so your page can show the error on a `429` too.

```js
const res = await fetch("https://app.hookie.ai/your-workspace/contact/aBcXyz…", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ email, message }),
});
if (res.ok) showThanks();
```

<Tip>
  A `FormData` body needs no preflight, because it is a form encoding. Without an allowed origin the submission is still stored, but your page cannot read the answer, and `fetch()` rejects with "Failed to fetch".
</Tip>

## 3. See it in the console

Open the project's **Datasets** tab to see the record as a table, and the **Overview** dashboard to watch your usage tick up. To see the body exactly as it arrived, before any rule reshaped it, search **Submissions** on the **Observability** tab. Every ID there links to the rest of its chain.

Open a record, or trace a submission, to see the **request** it arrived in: the method, content type, source IP, query string and headers, such as `X-GitHub-Event`. Credentials such as `Authorization` and `Cookie` are stored as `[redacted]`.

When a provider says Hookie returned an error, choose **Activity** in the endpoint's menu. It lists what the endpoint received and what it refused over the last 7 days, and why each request was refused (IP allowlist, rate limit, quota, disabled endpoint, content type, signature and more). Refused requests never count against your quota.

The **Observability** tab searches the last 24 hours by default; widen it with **Time range**, down to a custom window to the minute. Each entity has its own filters (a delivery's status, destination, response code and latency, an event's dataset, a submission's routing status), and **Trace an id** takes any record, submission, delivery, AI run or workflow run id, such as the `Hookie-Delivery-Id` your receiver logged, straight to its chain: the raw body, each record's payload, each delivery's destination and error, and each workflow run with every step's status. Switch on **Live** to watch events arrive as you send them. The filters are kept in the page address, so a view like "failed deliveries to Billing between 14:00 and 14:30" can be shared as a link.

To test the wiring end to end, use **Send a test event** in an endpoint's menu. It posts to the endpoint's real URL, then follows that event for up to 30 seconds and says what happened: delivered, failed (with the answer and whether it will be retried), held because a destination is disabled, still sending, or, only when your destinations' dataset filters confirm it, that no enabled destination accepts the dataset.

## Safe retries

A retry returns the original submission (`200`, with `"idempotent": true`) instead of creating a duplicate, and it never counts twice against your quota. Hookie recognises the delivery ids that webhook providers already send and keep across their retries, so Stripe, GitHub, Shopify, GitLab, Twilio, Linear, Twitch, Atlassian, Slack, Svix and every [Standard Webhooks](https://www.standardwebhooks.com) sender are deduplicated with nothing to configure. `deduplicated_by` in the answer says which id matched. Duplicates are tracked per endpoint, so two endpoints never collide.

From your own code, send an `Idempotency-Key`:

```bash
curl -X POST 'https://app.hookie.ai/your-workspace/orders/aBcXyz…' \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: order-1042" \
  -d '{"order":1042,"total":59.9}'
```

## Prefer a key?

Machine-to-machine senders can also use an **ingest key** (`ik_live_…`). Create one in the project's **Ingest keys** tab: it is stored hashed and shown once, and it can carry an expiry and an IP allowlist. See [Ingest keys](/ingest-keys) for rotating and revoking them.

```bash
curl -X POST 'https://app.hookie.ai/v1/ingest/ik_live_xxx/orders' \
  -H "Content-Type: application/json" \
  -d '{"order":1042,"total":59.9}'
```

## Route with rules

<Warning>
  Everything above routes by _address_: the URL names the dataset (the endpoint's own; a trailing `/{dataset}` may repeat it, and naming any other dataset is refused with `403`), and the payload is stored whole. There is nothing to decide, so **rules are not consulted on any of those requests.** Adding a rule and then posting to an endpoint URL is the one thing that looks like it should work and doesn't.
</Warning>

Rules are for the case where the sender _can't_ say where an event belongs, such as one stream carrying several kinds of event. They are evaluated by exactly one shape: an ingest key with **no dataset in the path**.

```bash
curl -X POST 'https://app.hookie.ai/v1/ingest/ik_live_xxx' \
  -H "Content-Type: application/json" \
  -d '{"type":"refund","order":1042,"total":59.9}'
```

Every enabled rule in the project is then tried against that payload. A rule's _conditions_ test paths in the payload, all of which must hold: `type` equals `refund`, `total` at least `50`, `country` in a list, or a bounded regular expression. They use the same ten operators as every other condition in Hookie (see [Conditions](/workflows#conditions)); in a rule, `equals`, `not_equals` and `in` compare as text, so `5` and `"5"` match. Its _mappings_ pick fields out into a record of your own shape. Leave conditions empty to match everything, and mappings empty to store the payload whole.

Build rules on the project's **Rules** tab. The rule editor has a row per condition, with an operator picker and a value field that fits the operator, rows for mappings, a dataset picker and a **Status** switch. **Test against a sample event** runs the rule over a payload, prefilled from the latest submission when it parses, and shows whether it matched and the record it would write, without storing anything. Each rule's menu has **Edit**, **Duplicate**, **Enable** or **Disable**, and **Delete**. Over the API, `PATCH /admin/api/projects/{pid}/rules/{id}` changes any field, validated as a create is, and `POST /admin/api/projects/{pid}/rules/test` with `{conditions, mappings, payload}` answers `{matched, record}` and writes nothing.

Rules are not first-match: every rule that matches writes its own record, so one event can land in several datasets at once. If none match, the response comes back with `"routed": []` and the raw submission is still captured. Find it under **Observability → Submissions**, which is how you tell "no rule matched" from "the event never arrived".
