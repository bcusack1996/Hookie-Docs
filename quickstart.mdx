This walks through the whole path an event takes in Hookie, in the console: an [endpoint](/concepts/endpoints) receives it, a [dataset](/concepts/datasets-and-records) keeps it, and a [destination](/concepts/destinations-and-deliveries) gets a signed copy. It takes about five minutes.

## 1. Sign in

[Sign in](https://app.hookie.ai/#/signin) with an emailed 6-digit code or GitHub. There is no password. Your first sign-in creates a free workspace with one project in it, called **Default**. You use that project throughout this guide.

## 2. Add an endpoint

<Steps>
  <Step title="Open the Default project">
    Choose **Projects** in the side navigation, then open **Default**.
  </Step>
  <Step title="Add the endpoint">
    Open the **Endpoints** tab and choose **Add endpoint**. Enter a **Name**, such as `Order events`. **Dataset** is optional: it defaults to the endpoint's name (`order_events`). Choose **Create**.
  </Step>
  <Step title="Copy its URL">
    The endpoint's card shows its **Public URL** with a copy button. The project's **Overview** tab shows the same URL under **Send events to this project**, with a ready-to-paste `curl` command.
  </Step>
</Steps>

The URL looks like this:

```http
https://app.hookie.ai/{workspace}/{project}/{endpoint-slug}
```

Hookie generates the endpoint slug, and it is high-entropy. **The URL is the endpoint's secret**: anyone who has it can send events, so there is no key to put in a header.

<Note>
  Creating a new project with **Create a project** and the **Webhook** type adds one endpoint for you, named after the project. Use that endpoint rather than adding a second one. The Default project starts with no endpoints.
</Note>

## 3. Send a test event

Open the endpoint's menu (**⋮** on its card) and choose **Send a test event…**. Edit the **Event payload (JSON)** if you like, then choose **Send test event**.

This is not a simulation. It posts to the endpoint's real URL, so the event is stored, routed and fanned out exactly like a live one. The dialog then follows the event for up to 30 seconds and says what happened to it. At this point you have no destination, so it tells you that nothing is delivered.

You can send the same thing from a terminal:

```bash
curl -X POST 'https://app.hookie.ai/your-workspace/default/aBcXyz…' \
  -H "Content-Type: application/json" \
  -d '{"order":1042,"email":"ada@example.com","total":59.9}'
```

Hookie answers with the submission ID and the datasets the event was stored in:

```http
201 Created
{
  "submission_id": "9d3f…",
  "routed": ["order_events"],
  "records": 1
}
```

## 4. See the record

Choose **View records** in the endpoint's menu. That opens the **Datasets** tab on the endpoint's dataset, with each event as a row. Choose **Refresh** to fetch events that arrived after the page loaded.

To see the body exactly as it arrived, search **Submissions** on the **Observability** tab. Every ID there links to the rest of its chain: the submission, its record, and every delivery made from it.

## 5. Add a destination

A destination is a URL of yours that Hookie sends each new record to, signed.

<Steps>
  <Step title="Open Connections">
    Open the project's **Connections** tab. Destinations are listed under **Destinations · outbound**.
  </Step>
  <Step title="Add the destination">
    Choose **Add destination**. Enter a **Name** and the **URL** of your receiver, which must be `https`. Leave **Dataset filter (optional)** empty to receive every dataset, or name datasets separated by commas. Choose **Create**.
  </Step>
  <Step title="Save the signing secret">
    The destination's signing secret is shown when you create it. Store it where your receiver can read it, so the receiver can [verify each delivery's signature](/signatures). Owners and admins can reveal it again later from the destination's card.
  </Step>
</Steps>

No receiver yet? Any HTTPS request inspector works for a first test. The Free plan includes one destination.

## 6. Watch the delivery

Send another test event from the endpoint's menu. This time the dialog reports the delivery: delivered, or failed with your receiver's answer and whether it will be retried.

Open the **Deliveries** tab to see every outbound attempt, newest first, with its status, destination, dataset, response and attempt count. Filter by status, destination and time. **Details** on a row shows the whole delivery, including your receiver's response. A delivery that did not arrive can be replayed, one at a time or all at once with **Replay matching**.

A failed delivery is retried for about a day. See [Destinations, deliveries and retries](/concepts/destinations-and-deliveries) for the schedule.

## Point an HTML form straight at an endpoint

An endpoint accepts what a browser actually posts, so a plain form needs no JavaScript and no backend of your own. Set `action` to your endpoint URL:

```html
<form action="https://app.hookie.ai/your-workspace/contact/aBcXyz…" method="post">
  <input name="name" required>
  <input name="email" type="email" required>
  <textarea name="message"></textarea>
  <button>Send</button>
</form>
```

The fields arrive as an ordinary record, stored whole into the endpoint's dataset:

```json
{
  "name": "Ada Lovelace",
  "email": "ada@example.com",
  "message": "Hello, world!"
}
```

Both form encodings work: `application/x-www-form-urlencoded` and `multipart/form-data`. A few details worth knowing:

- A field that repeats (checkboxes, a multi-select) becomes an **array** rather than losing all but one value.
- Field names are kept **verbatim and flat**. A field called `user.email` stays the key `user.email` and does not become a nested object.
- A **file** part is recorded as a descriptor and its bytes are discarded, in the record **and** in the raw submission. Hookie stores records, not blobs, so you get proof something was attached without the contents:
  ```json
  {
    "email": "grace@example.com",
    "attachment": { "filename": "report.pdf", "type": "application/pdf", "size": 18244 }
  }
  ```
- Everything else is still parsed as JSON regardless of its `Content-Type`, which is what most webhook providers send. A body that is not JSON but is sent as text, such as `text/plain`, XML, CSV or NDJSON, is stored as `{ "body": "<the text>", "content_type": "text/plain" }`. See the [API reference](/api-reference#ingest).

<Tip>
  Because the browser navigates to the endpoint on submit, the visitor lands on Hookie's JSON response. For a polished flow, submit with `fetch` and a `FormData` body (that is also a form encoding, so it needs no preflight), then show your own thank-you state.
</Tip>

## Safe retries

Send an `Idempotency-Key` and a retry returns the original submission instead of creating a duplicate. It never counts twice against your quota:

```bash
curl -X POST 'https://app.hookie.ai/your-workspace/default/aBcXyz…' \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: order-1042" \
  -d '{"order":1042,"total":59.9}'
```

## Sending from your own server

For your own code, use an **ingest key** (`ik_live_…`) rather than an endpoint URL. Create one on the project's **Ingest keys** tab with **Create key**; it is shown once. A key is also the only way to route with [rules](/concepts/rules-and-mappings) and to read the [live stream](/streaming).

```bash
curl -X POST 'https://app.hookie.ai/v1/ingest/ik_live_xxx/orders' \
  -H "Content-Type: application/json" \
  -d '{"order":1042,"total":59.9}'
```

See [Endpoints and ingest keys](/concepts/endpoints) for when to use which, and [Ingest keys](/ingest-keys) for rotating and revoking keys.

## Route with rules

Requests that name their dataset, which includes every endpoint URL, store the payload whole into that dataset, and **rules are not consulted**. Rules run only for an ingest key with no dataset in the path, `POST /v1/ingest/{key}`, where every matching rule writes its own record. See [Rules and mappings](/concepts/rules-and-mappings).
