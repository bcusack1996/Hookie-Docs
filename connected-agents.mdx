Hookie runs a hosted [MCP](https://modelcontextprotocol.io) server. Point an AI coding agent (Claude Code, Cursor, or any MCP client) at one URL and it can do, on your behalf, the things you would otherwise do in the console: create endpoints, write routing rules, point events at a destination, read records back, and replay a failed delivery.

Nothing is installed and nothing is pasted anywhere. The agent signs in as you, starts out read-only, and you decide in the console what more it may do. You can cut it off again in one click.

<Note>
  Hookie has no chat assistant of its own: you bring your agent. In the console, **Connect an agent** in the top bar (next to the theme switch and your profile) shows your MCP URL, the Claude connector, and the Claude Code command in one place.
</Note>

<Note>
  The [`hookie` CLI](/cli) is the same connection from a terminal instead: the same OAuth flow, the same credential store, and commands generated from the same catalog you see below — so anything an agent can call, you can run by hand.
</Note>

## Connect one

Hookie hosts the MCP server. There is nothing to install; point your agent at:

```http
https://app.hookie.ai/mcp
```

For Claude Code that is one command; or, in an `.mcp.json` that you can commit to a repo:

<CodeGroup>

```bash Claude Code
claude mcp add --transport http hookie https://app.hookie.ai/mcp
```

```json .mcp.json
{
  "mcpServers": {
    "hookie": {
      "type": "http",
      "url": "https://app.hookie.ai/mcp"
    }
  }
}
```

</CodeGroup>

For Claude on the web or desktop, add Hookie as a custom connector: open [Settings → Connectors](https://claude.ai/settings/connectors), choose **Add custom connector**, and paste the URL above. Claude then signs in to Hookie as you, the same way.

No credential goes in that file, because there isn't one to put there. The first request your agent makes is refused with a pointer to Hookie's authorization server (WorkOS AuthKit, the same place you sign in). The agent registers itself there, opens a sign-in in your browser, and from then on holds a token it refreshes on its own. That is the standard OAuth 2.1 authorization-code flow with PKCE, the same one you would get from any well-behaved MCP client.

## What it may do

Signing in proves _who_ the agent is acting for. _What_ it may do is decided separately, by you, in **Settings → Connected agents**. A newly connected agent can only read until you grant it more, and the change takes effect on its next call.

Access is **one level of three**, and each includes the one before it. Choose it with **Change access** beside the agent; the dialog says what each level allows.

| Level | Scope | Lets the agent… |
| --- | --- | --- |
| Read only | `hookie:read` | Read the workspace: projects, datasets, records, endpoints, rules, destinations, deliveries, triggers and workflows. |
| Read and write | `hookie:write` | Also create, change and delete endpoints, rules, destinations, workflows, sources, AI triggers, AI agents and the customer portal. Equivalent to the developer role. |
| Administer | `hookie:manage` | Also projects, cron and WebSocket triggers, and workspace administration: members, SSO, IP allowlist and audit export. Equivalent to admin. |

An agent is never a principal of its own. It acts _as you_, and its authority is your workspace role narrowed to the scopes you granted; whichever is more restrictive wins. An agent granted `hookie:manage` by someone with the viewer role is still a viewer.

### Two things it can never do

- **Touch billing.** Subscribing, cancelling, and changing a card are unreachable at every scope. Those stay decisions a person makes.
- **Destroy data in bulk.** There is no tool to delete a project, purge a dataset or close the workspace. An agent manages routing configuration, which is visible and undoable; bulk, irreversible deletion stays in the console, where it has to be typed out. The one exception is `delete_record`, which erases a **single** record by id (for an erasure request, or a secret posted by mistake) and is marked destructive so your client asks you first.

Every action an agent takes is written to your audit log with **you** as the actor and the agent's client ID recorded alongside, so "who deleted this endpoint" always has an honest answer.

### When an agent is refused

A call above the agent's level is refused with what to do about it, not a bare "Insufficient role". The 403 names the scope the call needs and the one the agent holds, and links to **Settings → Connected agents** opened on that agent:

```json
{
  "error": "This needs hookie:write, and this agent is approved for hookie:read. Ask your user to widen its access in the Hookie console under Settings → Connected agents (https://app.hookie.ai/#/settings/agents?client=…); it applies on the next request, with no need to reconnect.",
  "code": "agent_scope_insufficient",
  "required_scope": "hookie:write",
  "granted_scopes": ["hookie:read"],
  "manage_url": "https://app.hookie.ai/#/settings/agents?client=…"
}
```

Over MCP the same sentence comes back as the tool's error, so the agent can hand you the link. Widening applies to its very next call; an MCP client that cached its tool list sees the new tools once it lists them again.

Two refusals carry no link, because widening would not help:

- `code: "insufficient_role"` — **your own role** does not allow the call. An agent can never do more than you, so a workspace owner or admin has to change your role.
- `code: "agent_not_permitted"` — no agent may do this at any level: billing, platform administration, managing connected agents, and revealing or rotating a destination's signing secret.

## Revoke

**Settings → Connected agents** in the console lists everything you have connected, what each may do, and when it last acted. Revoking takes effect on the agent's next call, even though its token is still valid, because Hookie checks its own grant on every request.

Available with `hookie:manage` — the routes the console keeps to owners and admins:

| Tool | What it does |
| --- | --- |
| `create_project` | A new project. |
| `create_cron_trigger · update_cron_trigger · test_cron_trigger · delete_cron_trigger` | Cron triggers: a payload emitted on a schedule (five cron fields, at least 5 minutes apart, in an IANA time zone). Update changes any field; test fires it once, now, as a real event. |
| `create_ws_trigger · update_ws_trigger · test_ws_trigger · delete_ws_trigger` | WebSocket triggers: an outbound connection whose matching frames become events. Headers are encrypted and never returned. Update connects or disconnects; test returns the first frames without storing anything. |

There is no `create_dataset`, because a dataset is not something you create. A dataset is a name records carry: it exists the moment the first record is routed into it, and the console has no way to make an empty one either. Name it in a rule, an endpoint, or a workflow's `entry_dataset` and it appears.

Every tool carries MCP annotations, so a client can tell at a glance which calls are safe. `readOnlyHint` is derived from the tool's required scope rather than maintained by hand, so it cannot disagree with what the tool is allowed to do. `destructiveHint` is set only where something is genuinely unrecoverable — `delete_webhook`, `delete_rule`, `delete_destination`, `delete_record_view`, `delete_record` and `revoke_ingest_key`. It is deliberately **not** set on `delete_workflow`, which only deactivates, or on `replay_delivery` and `replay_deliveries`, which re-send: prompting for confirmation on a reversible action trains people to click through the ones that matter.

## Addressing an endpoint you just created

An endpoint's public URL is `{workspace}/{project}/{endpoint-slug}`, and the endpoint slug is a high-entropy value the server mints — not the readable `slug` you passed in, which is stored as `base_slug` and never appears in a URL.

You do not have to assemble any of that. `create_webhook` and `list_webhooks` both return `public_path` and `public_url`, and `public_path` is exactly the string `send_test_event` takes:

```json
{
  "id": "97249267-…",
  "base_slug": "orders",
  "version": "1",
  "webhook_slug": "aBcXyz0123456789abcdefgh",
  "public_path": "acme-3f9a/orders/aBcXyz0123456789abcdefgh",
  "public_url": "https://app.hookie.ai/acme-3f9a/orders/aBcXyz0123456789abcdefgh"
}
```

<Warning>
  `webhook_slug` **is the credential** — anyone holding it can post events to your workspace, which is why the URL needs no other authentication. So are `public_path` and `public_url`, which contain it. `base_slug` and `version` are the readable identity and are safe to log.
</Warning>

If you do need the pieces, `get_workspace` gives the first segment. A wrong path and a disabled endpoint both answer the same 404, so check `enabled` before assuming the URL is wrong.

The `update_` tools are narrower than they sound, deliberately. An endpoint's slug is the credential in its public URL, and its criteria and mappings define what it has already ingested; changing those in place would quietly reinterpret history. A destination's URL and signing secret are fixed for the same reason: a delivery's signature is verified against the URL it was sent to. To change any of them, create the replacement and delete the old one.

## Bringing your own client

The hosted server speaks MCP's Streamable HTTP transport at `https://app.hookie.ai/mcp`: POST JSON-RPC, no session header required. Authentication is standard OAuth 2.1, so any client that speaks it can connect without an MCP library. Start with our protected-resource document, which names the authorization server to register with:

```http
GET  https://app.hookie.ai/.well-known/oauth-protected-resource   # RFC 9728 — names the authorization server
GET  <issuer>/.well-known/oauth-authorization-server            # RFC 8414 — endpoints, PKCE methods
POST <issuer>/oauth2/register                                   # RFC 7591 — dynamic client registration
GET  <issuer>/oauth2/authorize                                  # authorization code + PKCE (S256 required)
POST <issuer>/oauth2/token                                      # code → access + refresh token
```

<Warning>
  Ask the authorization server only for the scopes it advertises (`openid`, `profile`, `email`, `offline_access`). Hookie's own `hookie:*` scopes are **not** requested there. They are granted by you in the console, and asking WorkOS for them fails the authorization outright.
</Warning>

PKCE is required, because agents are public clients that cannot keep a secret and the authorization code travels through a terminal. Registration is open because agents are installed per developer rather than registered by us ahead of time; a freshly registered client can only read until a human grants it more in the console. Hookie is the resource server: it verifies the access token offline against WorkOS's signing keys, then applies the grant you set. The token authenticates the same `/admin/api/*` routes the console itself calls, so there is no second, weaker API to learn.
