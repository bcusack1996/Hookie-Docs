Hookie exposes three HTTP surfaces: the public **ingest + streaming** API (authenticated by a path-form endpoint URL or an `ik_live_…` ingest key), the token-authed **customer portal** API for your end customers, and the **admin** API that drives the console (authenticated by your session in the browser, by an OAuth access token when a [connected agent](/connected-agents) is acting on your behalf, or by an [API key](/api-keys) for CI jobs, scripts and backends).

## Ingest

Bodies may be JSON, `application/x-www-form-urlencoded`, or `multipart/form-data`, so an HTML form can post straight to an endpoint with no JavaScript (see the [quickstart](/quickstart)). Anything else is read as JSON first, regardless of its `Content-Type`, which is what most webhook providers send; a body that parses is stored exactly as it arrived.

A body that is **not** JSON is kept as text when its `Content-Type` is textual: `text/*` (plain text, CSV, XML), `application/xml` and other `+xml` types, NDJSON / JSON Lines (`application/x-ndjson`), `application/csv` and YAML. That covers plain-text alerts, SOAP and other XML outbound messages, CSV exports and NDJSON batches. Hookie stores it as one event with the text verbatim:

```json
{ "body": "disk full on db-1", "content_type": "text/plain" }
```

Criteria and mappings address it as `body` and `content_type`. NDJSON is not split into one event per line. Malformed JSON sent as `application/json` (or with no `Content-Type`) is still refused with `400`, and a non-JSON body of any other type, such as `application/octet-stream`, is refused with `415`. Every body is capped at 1,000,000 bytes.

**Disabling an endpoint.** In the console, **Disable** asks you to confirm first. While an endpoint is disabled its URL answers `503` with `"reason": "endpoint_disabled"` and stores nothing; a URL that names no endpoint is still `404`. The difference matters to senders: providers treat a `404` as a dead URL and may switch the webhook off or drop events, but they retry a `503`, so events sent while it is disabled can still arrive if you enable it again within the provider's retry window.

**Rate limits.** Each credential (one endpoint URL, or one ingest key) accepts up to **100 requests per 10 seconds**, on every plan. Past that, or past your plan's monthly event quota, ingest answers `429` with a `Retry-After` header: `10` seconds for the burst limit and `3600` for the quota. The same value is in the body as `retry_after`. The [Data API](/data-api)'s per-key burst limit answers the same way, with `Retry-After: 10`.

**Key matching.** An ingest key is matched on the whole token, never on its visible prefix, and a revoked or expired key never matches, so no two keys can stand in for each other, on ingest or on `/v1/stream`.

`/v1/webhooks/{key}/{slug}` looks the slug up **in the key's project only**. A slug that belongs to another project, even in the same workspace, is `404`.

An endpoint applies **its own criteria and mappings** to every event it receives, on its public path-form URL as on `/v1/webhooks/{key}/{slug}`. Every criterion must hold, or the event is kept as a submission but makes no record, and `routed` comes back empty. Mappings pick fields into the record's shape; with none, the payload is stored whole. Project [mapping rules](/quickstart) are not evaluated on an endpoint, and not on `/v1/ingest/{ingest_key}/{dataset}`, which stores the payload whole into that dataset. Rules run on exactly one shape: `POST /v1/ingest/{ingest_key}` with no dataset, where every matching rule writes its own record and none matching leaves `routed` empty. A path-form endpoint writes only to its own dataset: a trailing `{dataset}` that names any other is refused with `403`, so a public form's URL cannot be used to write elsewhere in the project. To send one source into several datasets, use an ingest key. An endpoint can [verify its provider's signature](/endpoint-verification) (Stripe, GitHub, Shopify, Slack, Standard Webhooks or a generic HMAC) before anything is stored, an ingest key can require an HMAC signature, and a source-IP allowlist is enforced at every level that has one: the endpoint or key, the project and the workspace. An endpoint's URL and an ingest key can each be **rotated with an overlap**, and a key can **expire**; see [Ingest keys](/ingest-keys).

## Customer portal API

```http
# Authorization: Bearer <portal token>   (or the portal's session cookie)
POST   /portal/api/session                                   # trade the token for an 8-hour session cookie
GET    /portal/api/me                                        # portal name + branding, customer name, event types
GET    /portal/api/event-types                               # datasets the portal exposes
GET    /portal/api/examples                                  # a redacted example per dataset + the signature scheme
GET    /portal/api/destinations                              # the customer's destinations
POST   /portal/api/destinations                              # create (https only; signing secret shown once)
PATCH  /portal/api/destinations/{id}                         # edit name, URL, event types; pause or resume
DELETE /portal/api/destinations/{id}                         # delete
GET    /portal/api/destinations/{id}/secret                  # show the signing secret
POST   /portal/api/destinations/{id}/rotate-secret           # rotate, with a 24-hour overlap
POST   /portal/api/destinations/{id}/expire-previous-secret  # end the overlap early
GET    /portal/api/deliveries                                # deliveries to the customer's destinations
GET    /portal/api/deliveries/{id}                           # one delivery in full
POST   /portal/api/deliveries/{id}/replay                    # send it again
```

A separate, token-authed surface for your _end customers_, scoped to one portal and customer. The token is not accepted in the query string, and each token may make 60 calls a minute. See [Customer portal](/customer-portal) for issuing tokens and embedding.

## Admin API

The console's admin API lives at `/admin/api/projects/{pid}/…` and drives everything you see in the app. [Sign in](https://app.hookie.ai/) to explore it. It accepts a browser session, or `Authorization: Bearer` with either an OAuth access token, which is how a [connected agent](/connected-agents) reaches the very same routes, or an [API key](/api-keys) (`hk_…`). While a workspace is suspended, reads keep working and every write except billing answers `403` with `"reason": "workspace_suspended"`, for a connected agent or an API key exactly as for the console.

Every credential may make 100 requests every 10 seconds, after which the API answers `429` with `Retry-After: 10`. A `POST` may carry an `Idempotency-Key`, so a retry is answered once for 24 hours rather than run twice, and every response carries the API version in `Hookie-Version`. [API keys](/api-keys#rate-limits) covers all three.

The resources share one contract:

- **Get one by id.** `GET <resource>/{id}` returns the object under the resource's singular name (`rule`, `webhook`, `destination`, `source`, `trigger`, `view`, and so on), or `404`. Ingest keys use `ingest_key`, because a create's `key` is the plaintext token.
- **Creates return what they created**, under that same name, alongside every field they already returned.
- **Lists page.** Every configuration list takes `limit` (1 to 1,000, default 1,000) and `offset`, and adds `total`, `limit` and `offset` beside the array. The array keeps its name and shape, so a caller that sends neither gets every row, as before.

## Export, import and clone a project

A project's configuration can leave it as one document, and that document can build the same setup in another project. Use it to promote a pipeline from staging to production, or to start a new customer's project from a template. In the console, it is under the project's **Settings → Configuration**: **Export JSON**, **Export YAML**, **Import configuration (JSON)** and **Clone project**.

```http
GET  /admin/api/projects/{pid}/config               # the document, as JSON
GET  /admin/api/projects/{pid}/config?format=yaml   # the same, as YAML
POST /admin/api/projects/{pid}/config               # create in this project what a document describes
POST /admin/api/projects/{pid}/clone                # {name}: a new project with this one's configuration
```

The document is the same `hookie.yml` shape the CLI reads, so `hookie export` writes it and `hookie apply` applies it (see [Configuration](/cli/configuration)). Connected agents have `export_project_config` and `import_project_config`.

**What is in it:** endpoints (the newest version of each, with its criteria, mappings, dataset and IP allowlist, but not its [signature verification](/endpoint-verification), so an imported endpoint starts with none), rules, destinations (name, URL, dataset filter and delivery limits), AI agents, workflows, AI triggers, cron triggers and record views.

**What is never in it:**

- **Endpoint URLs.** An endpoint's URL is its credential. The document carries the endpoint's readable `slug` only, and every imported endpoint gets a new URL.
- **Signing secrets.** Every imported destination gets a new signing secret, so its receiver must be given the new one.
- **Ingest keys.** Create new keys in the target project.
- **Sources, WebSocket triggers and portals.** Their connection settings are encrypted credentials, and a portal belongs to its customers and their tokens. They are listed under `not_exported`, with a count and the reason, rather than silently dropped. Set them up again in the target project.
- **Destinations that belong to a portal customer**, and anything the project has received: records, submissions, deliveries and run history.

A workflow's `http` step headers are exported as stored, like the rest of the definition, which is why they should never hold a secret.

**Import only adds.** Each resource is created through its own create route, so it is validated, plan-limited and audited exactly as if you had created it by hand. A resource whose identity already exists in the project is skipped, never overwritten: an endpoint by its slug, a record view by its dataset and name, everything else by its name. An AI agent is exported with a `ref`, and a workflow's `agent_call` that names that ref is pointed at the agent created (or found) in the target project. One request imports at most 250 resources. The console imports JSON files; import YAML with `hookie apply`. The response lists what was `created`, `skipped` and `failed`, with `ok: false` if anything failed. To bring an existing project in line with a document, changes included, use `hookie apply`, where you review the diff first.

**Endpoint slugs are unique in the workspace**, not just the project. So an endpoint imported into another project of the same workspace, which is always the case for a clone, cannot keep its slug. It is created as `{slug}-copy`, or `-copy-2` up to `-copy-5` if that is taken too, and its entry in `created` carries a `note` saying so. A second import of the same document recognises the copy and skips it. The public URL is minted fresh either way, so the slug change affects only the endpoint's label.

**Clone** creates a new project of the same type, without the starter endpoint a new project normally gets, and imports the source project's export into it. It answers `201` with the new `project` and the `import` result. Importing needs the developer role or above; cloning creates a project, so it needs owner or admin.

## Request headers

| Header | Purpose |
| --- | --- |
| `Content-Type` | On ingest: application/json, application/x-www-form-urlencoded, multipart/form-data, or a text type (`text/*`, XML, CSV, NDJSON), which is stored as `{ body, content_type }` when the body is not JSON. Any body that parses as JSON is read as JSON. |
| `Idempotency-Key` | Optional. Dedupes retries per endpoint (on `/v1/ingest`, per key); the same submission is returned and never double-counted. Without it, a provider's own delivery id is used: `webhook-id` (Standard Webhooks), `svix-id`, `X-GitHub-Delivery`, `X-Shopify-Webhook-Id`, `X-Gitlab-Event-UUID`, `I-Twilio-Idempotency-Token`, `Linear-Delivery`, `Twitch-Eventsub-Message-Id`, `X-Atlassian-Webhook-Identifier`, or Stripe's `evt_` id or Slack's `event_id` in the body. On a `POST` to `/admin/api`, it makes the call safe to retry: the first response is stored for 24 hours and replayed with `Idempotent-Replayed: true` (see [Idempotent retries](/api-keys#idempotent-retries)). |
| `Hookie-Version` | Optional, on `/admin/api` and `/mcp`. Pins the API version; an unsupported one is refused with `400` and `supported_versions`. Every response carries the current one, `2026-09-29`. See [Versioning](/api-keys#versioning). |
| `Origin` | On an endpoint URL: when it is one of the endpoint's allowed origins, the response carries `Access-Control-Allow-Origin`, and `OPTIONS` answers the preflight. |
| `X-Hookie-Signature` | Required only for keys with signature enforcement. `t=<unix>,v1=<hex>` over `<t>.<body>`. `t` must be within 5 minutes of now, and several `v1=` values may be sent while you rotate the secret. |
| `Hookie-Hop` | Optional. How many times this event has already passed through Hookie. Hookie sets it on its own deliveries; a relay that forwards a delivery back into Hookie should pass it on. At 8 the request is refused with `508`. |
| `Authorization` | `Bearer <ingest_key>` for `GET /v1/stream` (or `?key=` for EventSource); `Bearer <access token>` for `/admin/api/*` and `/mcp` as a connected agent; `Bearer <hk_… API key>` for the same routes as an [API key](/api-keys). |

## Request details

Every submission keeps the request it arrived in: the method, the headers (at most 64, about 8 KB), the query string, the `Content-Type` and the source IP. Credentials are never kept: `Authorization`, `Cookie`, and any header or query parameter named like a key, token, secret, password or session is stored as `"[redacted]"`, and Cloudflare's own proxy headers are dropped. `GET /admin/api/projects/{pid}/records/{id}` and the correlation chain return it as `request`.

## HTML forms, CORS and URL verification

These are per-endpoint settings, set in the console's **Edit…** form or with `PATCH /admin/api/projects/{pid}/webhooks/{id}`. They apply to the endpoint's public URL only; ingest-key routes never answer CORS.

- `redirect_url`: an `https://` page that a browser's native form post is sent to (`303`) once it is stored.
- `cors_origins`: up to 20 origins (`https://example.com`, with no path), or `"*"`, whose `fetch()` may call the URL. The endpoint answers the `OPTIONS` preflight (`Access-Control-Allow-Methods: POST`, `Access-Control-Allow-Headers: Content-Type, Idempotency-Key`) for them. By default no origin is allowed.
- `handshake`: the provider URL check that the endpoint answers without storing anything or counting it against your quota. Choose one of `slack` (`url_verification`), `meta` (`GET ?hub.challenge`, checked against your verify token), `graph` (Microsoft Graph's `?validationToken`), `zoom` (`endpoint.url_validation`, signed with your secret token) or `twitch` (`webhook_callback_verification`). `handshake_secret` holds Zoom's secret token or Meta's verify token. It is stored encrypted and never returned; `list` only says `handshake_secret_set`.

## Refused requests

Every request that is refused once its endpoint or key is known is logged with its reason, status, time and source IP: IP allowlist, signature, quota, burst rate limit, disabled endpoint, body too large, unsupported or unparseable body, loop, failed URL verification, disallowed browser origin, and suspended workspace. Repeats of one reason are counted per minute. The log is kept for your plan's retention window, and refused requests never count against your quota. `GET /admin/api/projects/{pid}/webhooks/{id}/activity` (also the console's **Activity**, the `get_webhook_activity` MCP tool and `hookie endpoints activity`) lists an endpoint's received and refused requests for the last 7 days, newest first, with counts for the last 24 hours. A request to an unknown URL or key is not logged, because until it resolves there is no workspace to log it against.

## Response codes

| Status | Meaning |
| --- | --- |
| `201 Created` | Event stored and routed. |
| `200 OK` | Duplicate: the original submission is returned, with `deduplicated_by`. Also the answer to a provider's URL-verification challenge. |
| `303 See Other` | A browser's native form post to an endpoint with a redirect URL. `Location` is that URL. |
| `400 Bad Request` | The body declares JSON (or no `Content-Type`) and is not valid JSON, or is not a well-formed form encoding. |
| `401 Unauthorized` | Missing or invalid inbound signature (when required), or missing stream key. On an endpoint with [signature verification](/endpoint-verification), `reason` is `missing_header`, `bad_signature` or `stale_timestamp` and `scheme` names the check. Nothing is stored or counted. |
| `403 Forbidden` | Source IP not in the allowlist, or an agent token without the scope for this call. With `"reason": "workspace_suspended"`, the workspace has been suspended: nothing is stored or counted, so retry once it is reinstated. |
| `404 Not Found` | Unknown, revoked or expired ingest key, or unknown webhook endpoint (on `/v1/webhooks/{key}/{slug}`, one outside the key's project; on an endpoint URL, a rotated-away URL past its overlap). |
| `415 Unsupported Media Type` | The body is not JSON and its `Content-Type` is neither a form encoding nor a text type. The error names the type. |
| `422 Unprocessable Entity` | The JSON body has no fields (`{}`), so there is nothing to store. |
| `429 Too Many Requests` | Ingest burst limit (100 requests per 10 seconds per endpoint URL or ingest key) or the monthly event quota. Both send a `Retry-After` header (10 and 3600 seconds) and the same value as `retry_after` in the body. On `/v1/stream`, the plan's concurrent-connection cap. |
| `503 Service Unavailable` | The endpoint is disabled (`"reason": "endpoint_disabled"`). Nothing is stored; enable it to resume. |
| `508 Loop Detected` | The `Hookie-Hop` header says this event has already been through Hookie 8 times. That almost always means a destination is delivering back into an endpoint that feeds it. Nothing is stored. |

## Outbound (to your endpoints)

Deliveries are signed twice and carry `Hookie-Signature`, the [Standard Webhooks](https://www.standardwebhooks.com) headers `webhook-id`, `webhook-timestamp` and `webhook-signature`, `Hookie-Event-Id`, `Hookie-Delivery-Id` and `Hookie-Hop`. Delivery is at-least-once and unordered, so dedupe on the event ID and [verify the signature](/signatures). A 5xx, a network error, or a `404`, `408`, `409`, `425` or `429` is retried after about 5 s, 5 min, 30 min, 2 h, 5 h, 10 h and 10 h (eight attempts over roughly a day, with jitter, and never sooner than a `Retry-After` your service sends). Any other 4xx means your service refused the request, so it is not asked again: the delivery is marked `dead` after that one attempt, with the error `HTTP 4xx (not retried: the receiver refused the request)`. A dead delivery can be replayed.

A delivery waiting on a **disabled** destination is `paused`, not failed. It keeps its last response and is sent when the destination is enabled again. A delivery whose destination was **deleted** is `cancelled`. Neither counts as a failure. A destination's dataset filter is a list of dataset names; leave it out (or send `null`) for every dataset. An empty list is refused, since it used to mean "every dataset" rather than "none"; to stop deliveries, disable the destination. Creating a destination whose URL is one of the same project's own endpoint URLs or ingest keys, with a filter that admits the dataset it writes to, still succeeds but returns a `warning`: every event would loop back until `Hookie-Hop` stops it. An event acknowledged with `201` is fanned out even if the first attempt at that fails: it is re-driven every few minutes for about eight hours, and if it still cannot be, the workspace audit log records a `fanout_abandoned` entry. Rows polled by a database source, events from cron and WebSocket triggers, the record a workflow's `call_ai` step writes to its `output_dataset`, a workflow's `emit_event` records (unless the step sets `deliver: false`), and an AI trigger's output record fan out exactly like ingested ones, including that re-drive. An AI trigger's output fires no AI trigger and starts no workflow, and an emitted record starts no workflow, so neither can loop.

### Replaying in bulk

`GET /admin/api/projects/{pid}/deliveries/{id}` returns one delivery with its latest response body (16 KiB) and `attempts`: every attempt it made, oldest first, each with its time, `ok`, `status_code` (null when nothing answered: a timeout or a refused connection), `response_ms`, `error` and the first 512 characters of the response body. So a timeout, then a `502`, then a `401` are three attempts, not one. `attempts_not_recorded` counts attempts made before attempt history was kept. Attempts are kept for your plan's retention window.

`GET /admin/api/projects/{pid}/deliveries/metrics?window=24h` (or `7d`, `30d`; add `destination_id` for one destination) is delivery health per destination and in total: deliveries by outcome and their `success_rate`, attempts and `attempt_success_rate`, `latency_ms` percentiles (`p50`, `p95`, `p99`, over every attempt, so a timeout counts as its full timeout), failed attempts by class in `errors` (`3xx`, `4xx`, `5xx`, `timeout`, `connection`, `other`), and a `series` of ok and failed attempts per hour (per day for `30d`). The Deliveries tab shows it as **Destination health**; the `get_delivery_metrics` MCP tool and `hookie deliveries metrics` read it.

`POST /admin/api/projects/{pid}/deliveries/replay` replays every delivery that did not arrive, by filter: `destination_id`, `status` (`dead`, `failed`, or both, the default), `since` and `until` (ISO 8601), and `limit` (1 to 500, default 100). Only `dead` deliveries and `failed` ones with no retry scheduled match, only the latest delivery of each event to each destination, and only while the event is stored. It works oldest first and answers `{queued, matched, remaining, more}`: call it again while `more` is `true`. Send `dry_run: true` to get `{matched}` without sending anything. Each replay is charged to the monthly delivery allowance; when it runs out the call stops (`stopped: "delivery_allowance_exhausted"`), or answers `429` if it could queue none. The Deliveries tab's **Replay matching** button, `hookie replay --since 1h --failed` and the `replay_deliveries` MCP tool all use this route.

### Delivery settings

`PATCH /admin/api/projects/{pid}/destinations/{id}` also takes a destination's delivery limits: `timeout_seconds` (1 to 30, default 10), `max_per_second` (0.1 to 1000 deliveries a second) and `max_concurrency` (1 to 100 requests in flight). `null` restores the default. A delivery over the rate or the concurrency cap is **deferred**: it waits on the queue for its turn, is not failed, and does not use up one of its eight attempts. `POST …/destinations/{id}/rotate-secret` keeps the previous signing secret signing for 24 hours ([Verify signatures](/signatures#rotating-the-secret)); `POST …/destinations/{id}/expire-previous-secret` ends that window early.

### The monthly delivery allowance

A **delivery** is one event sent to one destination, and each plan includes a number of them a month: 1,000 on Free, 90,000 on Pro and 600,000 on Team, with a 10% grace on the paid plans. A delivery is counted when the fan-out creates it. Retries of it are not counted again, and neither is an event whose fan-out is re-driven. A **replay** is a new delivery and is counted; when nothing is left it is refused with `429` and `reason: "delivery_allowance_exhausted"`.

Past the allowance, events are still received, stored and routed. Their deliveries are **held**, never dropped: `GET /admin/api/projects/{pid}/deliveries/held` lists held events oldest first, with the month's `allowance` (`used`, `quota`, `ceiling`). `POST /admin/api/projects/{pid}/deliveries/held/release` sends them once there is room (a new month, or a plan upgrade). It works oldest first, and it stops at the first event it cannot fully cover, so events go out in the order they arrived. The console shows the month's count on Home and a **Send held deliveries** button on a project's Deliveries tab; MCP agents have `list_held_deliveries` and `release_held_deliveries`. A held event that ages past your plan's retention is pruned along with it, since there is nothing left to send.
