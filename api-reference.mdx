Hookie exposes three HTTP surfaces: the public **ingest + streaming** API (authenticated by a path-form endpoint URL or an `ik_live_…` ingest key), the token-authed **customer portal** API for your end customers, and the **admin** API that drives the console (authenticated by your session in the browser, or by an OAuth access token when a [connected agent](/connected-agents) is acting on your behalf).

## Ingest

Bodies may be JSON, `application/x-www-form-urlencoded`, or `multipart/form-data`, so an HTML form can post straight to an endpoint with no JavaScript (see the [quickstart](/quickstart)). Anything else is read as JSON regardless of its `Content-Type`, which is what most webhook providers send.

An endpoint applies **its own criteria and mappings** to every event it receives, on its public path-form URL as on `/v1/webhooks/{key}/{slug}`. Every criterion must hold, or the event is kept as a submission but makes no record, and `routed` comes back empty. Mappings pick fields into the record's shape; with none, the payload is stored whole. Project [mapping rules](/quickstart) are not evaluated on an endpoint, and not on `/v1/ingest/{ingest_key}/{dataset}`, which stores the payload whole into that dataset. Rules run on exactly one shape: `POST /v1/ingest/{ingest_key}` with no dataset, where every matching rule writes its own record and none matching leaves `routed` empty. A path-form endpoint writes only to its own dataset: a trailing `{dataset}` that names any other is refused with `403`, so a public form's URL cannot be used to write elsewhere in the project. To send one source into several datasets, use an ingest key. An ingest key can require an HMAC signature, and a source-IP allowlist is enforced at every level that has one: the key, the project and the workspace.

## Streaming

```http
GET  /v1/stream                         # live tail (SSE or WebSocket)
```

See [Live streaming](/streaming) for SSE/WebSocket details and resume.

## Customer portal API

```http
# Authorization: Bearer <portal token>   (or ?token=…)
GET  /portal/api/me                     # portal + customer info + event types
GET  /portal/api/event-types            # datasets the portal exposes
GET  /portal/api/destinations           # the customer's destinations
POST /portal/api/destinations           # create (https only; signing secret shown once)
PUT  /portal/api/destinations/{id}      # enable/disable or change URL
GET  /portal/api/deliveries             # deliveries to the customer's destinations
```

A separate, token-authed surface for your _end customers_, scoped to one portal and customer. See [Customer portal](/customer-portal) for issuing tokens and embedding.

## Admin API

The console's admin API lives at `/admin/api/projects/{pid}/…` and drives everything you see in the app. [Sign in](https://app.hookie.ai/) to explore it. It accepts either a browser session or `Authorization: Bearer` with an OAuth access token, which is how a [connected agent](/connected-agents) reaches the very same routes. Project-scoped resources:

| Resources | Covers |
| --- | --- |
| `datasets · submissions · rules · webhooks` | Routing: raw capture, mapping rules, versioned endpoints. |
| `ingest-keys · destinations · deliveries` | Credentials, outbound sinks, delivery log + replay. |
| `sources · triggers · cron-triggers · ws-triggers` | DB polling, AI triggers, scheduled + WebSocket sources. |
| `workflows · workflow-instances · ai-agents` | Multi-step workflows, instance history, reusable AI agents. |
| `search/{events,deliveries,ai-runs} · search/correlate/{id}` | Filtered search + cross-entity correlation. `q` matches the payload as literal text, ignoring case for any letter. Each result's `payload` is a preview of the first 2,000 characters; `payload_truncated` and `payload_length` say when it was cut. |
| `portals (+ /tokens)` | Customer portals and per-customer access tokens. |
| `telemetry (+ /test)` | [Broadcast Logs](/broadcast-logs): the project's one OTLP integration (Datadog, Grafana Cloud, OpenTelemetry Collector, PostHog or Sentry) and its test event. |

Workspace-level resources sit directly under `/admin/api/…` with no `{pid}` segment:

| Resources | Covers |
| --- | --- |
| `me · dashboard/{summary,timeseries}` | Signed-in user, workspace + plan, usage rollups. |
| `projects` | List, create and manage the projects everything else hangs off. |
| `audit` | Audit log, with CSV export (UTF-8 with a BOM; cells a spreadsheet would run as a formula are neutralised). |
| `ip-allowlist` | The workspace IP allowlist: `GET` to read it, `PUT {"ip_allowlist": [...]}` to replace it (`[]` allows every address). Owners and admins. |
| `agents` | Coding agents you have connected over OAuth — list and revoke. |
| `sso` | SAML configuration (Team plan). |
| `destination-presets · source-presets` | Integration presets for outbound sinks and sources. |
| `billing · stream` | Subscription state and the live event tail. |

## Request headers

| Header | Purpose |
| --- | --- |
| `Content-Type` | application/json, application/x-www-form-urlencoded, or multipart/form-data on ingest. Anything else is read as JSON. |
| `Idempotency-Key` | Optional. Dedupes retries; the same submission is returned and never double-counted. |
| `X-Hookie-Signature` | Required only for keys with signature enforcement. `t=<unix>,v1=<hex>` over `<t>.<body>`. `t` must be within 5 minutes of now, and several `v1=` values may be sent while you rotate the secret. |
| `Hookie-Hop` | Optional. How many times this event has already passed through Hookie. Hookie sets it on its own deliveries; a relay that forwards a delivery back into Hookie should pass it on. At 8 the request is refused with `508`. |
| `Authorization` | `Bearer <ingest_key>` for `GET /v1/stream` (or `?key=` for EventSource); `Bearer <access token>` for `/admin/api/*` as a connected agent. |

## Response codes

| Status | Meaning |
| --- | --- |
| `201 Created` | Event stored and routed. |
| `200 OK` | Idempotent replay. The original submission is returned. |
| `400 Bad Request` | Body is not valid JSON or is not a well-formed form encoding. |
| `401 Unauthorized` | Missing/invalid inbound signature (when required), or missing stream key. |
| `403 Forbidden` | Source IP not in the allowlist, or an agent token without the scope for this call. |
| `404 Not Found` | Unknown ingest key or webhook endpoint. |
| `422 Unprocessable Entity` | The JSON body has no fields (`{}`), so there is nothing to store. |
| `429 Too Many Requests` | Ingest burst rate limit or the monthly event quota (both send retry_after); on `/v1/stream`, the plan's concurrent-connection cap. |
| `508 Loop Detected` | The `Hookie-Hop` header says this event has already been through Hookie 8 times. That almost always means a destination is delivering back into an endpoint that feeds it. Nothing is stored. |

## Outbound (to your endpoints)

Deliveries are signed and carry `Hookie-Signature`, `Hookie-Event-Id`, `Hookie-Delivery-Id` and `Hookie-Hop`. Delivery is at-least-once and unordered, so dedupe on the event ID and [verify the signature](/signatures). A 5xx, a network error, or a `404`, `408`, `409`, `425` or `429` is retried after about 5 s, 5 min, 30 min, 2 h, 5 h, 10 h and 10 h (eight attempts over roughly a day, with jitter, and never sooner than a `Retry-After` your service sends). Any other 4xx means your service refused the request, so it is not asked again: the delivery is marked `dead` after that one attempt, with the error `HTTP 4xx (not retried: the receiver refused the request)`. A dead delivery can be replayed.

A delivery waiting on a **disabled** destination is `paused`, not failed. It keeps its last response and is sent when the destination is enabled again. A delivery whose destination was **deleted** is `cancelled`. Neither counts as a failure. A destination's dataset filter is a list of dataset names; leave it out (or send `null`) for every dataset. An empty list is refused, since it used to mean "every dataset" rather than "none"; to stop deliveries, disable the destination. Creating a destination whose URL is one of the same project's own endpoint URLs or ingest keys, with a filter that admits the dataset it writes to, still succeeds but returns a `warning`: every event would loop back until `Hookie-Hop` stops it. An event acknowledged with `201` is fanned out even if the first attempt at that fails: it is re-driven every few minutes for about eight hours, and if it still cannot be, the workspace audit log records a `fanout_abandoned` entry. Rows polled by a database source, and events from cron and WebSocket triggers, fan out exactly like ingested ones.
